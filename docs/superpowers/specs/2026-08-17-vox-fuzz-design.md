# vox-fuzz v1 — Design

Date: 2026-08-17 (revised same day: vox-fuzz is written in Vox)
Status: awaiting approval
Scope: fuzzing tool for code generated by the Vox compiler (Vox-lang/vox),
written in Vox itself.

## Purpose

Vox's safety story is that all failure surfaces through compile-time
rejection or runtime error flags: out-of-bounds access sets an error flag
and returns 0; writes past a fixed buffer's end are refused; buffer
overflow is documented as impossible. vox-fuzz attacks that claim
mechanically.

vox-fuzz is written in Vox. This is deliberate, and load-bearing for the
project's credibility: the language claimed to be memory-safe and highly
capable builds its own adversarial tooling. Trust in findings does not
depend on trusting the fuzzer — every finding is a `.vox` repro file that
anyone can compile and run to observe the failure independently. Building
a large real program in a young language is also dogfooding: compiler
bugs and ergonomic gaps hit during development are findings in their own
right and are filed against vox as they occur.

## The invariant (what counts as a finding)

For any Vox program and any runtime input:

1. The compiler must not panic (no ICE).
2. The compiler's emitted assembly must be accepted by nasm and ld.
3. The emitted binary must never die by signal (SIGSEGV, SIGBUS, SIGILL,
   SIGFPE, SIGABRT, ...).
4. The emitted binary must terminate within the harness timeout.
5. Compiling the same source twice must produce identical assembly.

A **nonzero exit code is not a finding** — Vox programs exit nonzero
legitimately. Only signal deaths, hangs, ICEs, toolchain rejections, and
nondeterminism are findings.

No differential oracle in v1 (deferred until the project owner has
evaluated the concept). The generator module is the documented seam.

## Child-death observation (POC-proven, no compiler changes needed)

The fuzzer's core observation is "how did the child die?" and its core
defense is "stop a hung child." Vox's native `reap` discards the wait4
status (NULL status pointer in `REAP_CHILD`) and there is no kill — but
neither is a blocker. The proven mechanism (POC: 2026-08-17, all four
classifications correct on vox 0.3.7):

- fork; child `Execute`s `/bin/sh -c "<cmd>; echo $? > status"` where
  `<cmd>` runs the target under `timeout(1)`; parent reaps, reads the
  status file, parses the number with a `byte N of` loop.
- `$?` decodes everything needed: `0` clean, `1–100` program exit codes,
  `124` hang (timeout killed it), `> 128` death by signal `N − 128`.
- **Generator constraint making this unambiguous:** generated programs
  only emit `exit with code 0–100`, so 124/126/127/128+ are reserved
  classifier values that no legitimate program can produce.

Cost: one extra sh spawn and a file round-trip per execution — noise
next to the compile step. Runtime deps: `/bin/sh`, coreutils `timeout`
(dev-tool territory, fine).

**Deferred vox ergonomics (roadmap, nothing waits on them):** native
reaped-status access (e.g. `the reaped exit code` / `the reaped signal`)
and `Send signal <N> to process <pid>.` (kill(2)) would drop the shell
wrapper entirely. Surface wording is the language owner's call. Also
noted for vox: `times` as an alias for `multiply` (dogfood finding —
`n times 10` reads more naturally than `n multiply 10`).

## Architecture

A Vox program (single repo, multiple `.vox` sources + vox lib files as
the module story allows). Two fuzzing loops share one execution harness
and one findings store.

```
generate ──▶ .vox text ──▶ [vox compile] ──▶ harness ──▶ classify ──▶ findings
    ▲                                           ▲                        │
seeded PRNG                                mutate (stdin/argv)        reduce
```

### Generator

Recursive-descent **text emitter**: grammar rules encoded as functions
that append rendered Vox source directly into a dynamic buffer, with an
explicit list-based scope/context stack (no AST data structure — Vox has
no ADTs, and the AST's only v1 consumer was the deferred oracle).
Constructs covered: variables, integer/decimal arithmetic, comparisons,
strings, dynamic and fixed buffers, lists, `while`/`for`/ranges,
`if`/`Otherwise` chains, functions, `On error` handlers, `print`,
`exit with code`, stdin/argv reads.

Weighted choice under a node budget, driven by a seeded xorshift PRNG
implemented in Vox; a given (seed, generator version) always yields the
same program. Scope tracking keeps programs valid by construction; the
**compile-clean rate** is reported per run (target ≥95%) — a falling
rate means generator drift, not compiler bugs.

### Harness

- `fork` + `Execute` for every child (vox itself, and fuzzed binaries),
  via the sh-wrapper mechanism above.
- Fresh temporary working directory per run (generated programs may
  legitimately create and write files); nothing runs in the repo tree.
- Wall-clock timeout: `timeout(1)` inside the wrapper (SIGKILL via
  `timeout -k` grace).
- Classification from the wrapper's status file: exit code, signal
  (status − 128), or hang (124).
- Parallel workers via fork; workers share nothing and write findings to
  the filesystem, the parent reaps and aggregates.
- **Caging (v1):** temp-dir isolation + timeout only. Resource limits
  (memory, file size) are a later vox feature or an optional external
  wrapper; the generator also does not emit mount/reboot/device-node or
  absolute-path file actions, so generated programs cannot reach outside
  their sandbox dir by construction.

### Mutator (`input` loop)

Byte/bit flips, boundary integers, block duplication/deletion/splice,
growth and truncation, non-UTF8 injection, token dictionary from the
target's string literals. Corpus-seeded (`vox/tests/` works). Black-box;
no coverage guidance in v1.

### Findings

`findings/<category>/<id>/`: `program.vox`, inputs, emitted asm
(`--emit-asm` re-run), a plain-text classification record (category,
signal, seed, generator + vox versions), and `repro.sh`. Categories:
`ice`, `asm-reject`, `crash`, `hang`, `nondeterministic`. Dedup by
category + signal + FNV hash (in Vox) of normalized source; duplicates
increment a counter.

### Reducer

Statement-level pruning over the rendered source text: drop a statement
(or balanced block), recompile, re-test, keep the smallest reproducer.
Line-oriented, respecting Vox's period/blank-line block rules. Budget-
capped per finding. Input findings: chunk removal and truncation.

## CLI

```
vox-fuzz gen    [--seed N] [--count N | --forever] [--jobs N]
                [--timeout MS] [--vox PATH] [--out DIR] [--budget N]
vox-fuzz input  <target.vox> [--corpus DIR] [--jobs N] [--timeout MS]
                [--vox PATH] [--out DIR]
vox-fuzz repro  <finding-dir>
```

Parsed via `arguments's all`. `--vox` defaults to `vox` on PATH, then
`../vox/target/release/vox`.

## Testing vox-fuzz itself

- Generator golden tests: fixed seeds → known source text.
- Integration: generated programs must compile with the real vox binary;
  compile-clean rate asserted in CI.
- Harness classification tests against fixture programs (clean exit,
  nonzero exit, deliberate SIGSEGV via a crafted asm fixture, hang).
- Findings round-trip: classify → save → `repro.sh` reproduces.
- Compiler bugs / ergonomic gaps hit while *writing* vox-fuzz are filed
  against Vox-lang/vox as they occur (dogfooding is part of the product).

## CI (GitHub Actions)

Clone + build vox, build vox-fuzz with it, run the
test suite, then a fixed-seed ~2-minute smoke fuzz. Any finding fails
the job and uploads the findings dir as an artifact.

## Out of scope for v1 (seams documented)

- Differential/semantic oracle — plugs in at the generator seam.
- Coverage-guided fuzzing.
- rlimit-grade resource caging (needs a vox feature or wrapper).
- File-channel input fuzzing beyond stdin/argv.
- Non-x86_64 targets.

## Phasing

- **Phase 1**: harness + classification (grows from the proven POC:
  fork/Execute/sh-wrapper/reap/status-parse). Gate: classification tests.
- **Phase 2**: generator + PRNG + compile-clean metric. Gate: ≥95% rate
  over 10k seeds.
- **Phase 3**: gen loop end-to-end + findings store + reducer.
- **Phase 4**: input loop + mutator + corpus handling.
- **Phase 5**: CLI polish, CI, README.
