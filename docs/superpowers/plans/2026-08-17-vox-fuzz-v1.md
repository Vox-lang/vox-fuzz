# vox-fuzz v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build a fuzzer, written in Vox, that generates random valid Vox
programs, compiles and runs them, and reports every case where a
vox-produced binary dies by signal, hangs, fails to compile, or compiles
nondeterministically.

**Architecture:** A Vox program split into `see`-included modules. A
seeded LCG drives a recursive text emitter that writes `.vox` source into
a growing buffer. Each generated program is compiled by the real `vox`
binary, then **supervised natively**: forked, `Execute`d, polled with
non-blocking reap against a deadline, `Send signal 9` if it overruns, and
its fate read from `the reaped status` — the kernel's own wait status,
undecoded. Findings are written to disk as self-contained repro
directories and shrunk by line-pruning.

**Tech Stack:** Vox (built from `../vox`), bash for the test runner and
Makefile, GitHub Actions for CI. Runtime deps: `nasm` and `ld` (via vox
itself), plus `/bin/sh` for the two jobs Vox cannot yet do — redirecting a
child's output to a file, and the line surgery in the reducer.

> **This plan was revised on 2026-08-18.** As first written it supervised
> every fuzzed program through `/bin/sh -c "timeout N cmd; echo $? >
> status"`, because vox 0.3.7 discarded the `wait4` status and gave a Vox
> program no way to recover a child's fate. **That is no longer true.**
> 0.4.0 shipped `the reaped status`, `reap ... without waiting`, and
> `Send signal`, which is exactly a supervisor's three pieces, and
> `examples/supervisor.vox` in the compiler repo is that loop as a
> runnable program. Task 3 below is the rewritten harness, verified by
> POC against vox 0.4.1 before this revision was written.
>
> The change is not cosmetic. Reading `$?` through a shell conflates a
> program that *exits with* code 139 with one *killed by* signal 11, and
> that ambiguity was the sole reason the original plan forbade the
> generator from emitting exit codes above 100. A real wait status keeps
> the two halves apart, so that restriction is gone and the generator may
> emit any exit code.

**Spec:** `docs/superpowers/specs/2026-08-17-vox-fuzz-design.md`

## Global Constraints

- **The tool is written in Vox.** No Rust, Python, or C in the fuzzer
  itself. Bash is allowed only for the test runner, Makefile, and CI.
- **Vox binary under test:** `../vox/target/release/vox` by default,
  overridable with `--vox PATH`.
- **`VOX_CORE_PATH` MUST be set to the repo's coreasm directory** for
  every invocation of the vox binary. Verified in `vox/src/main.rs:79`:
  the environment variable has highest priority, and when it is unset an
  installed `/usr/share/vox/coreasm` (present on this machine, from the
  0.3.7 package) silently wins over the repo copy. Without this, the
  fuzzer tests the *installed* runtime while appearing to test the
  development one — every finding and every clean run would be about the
  wrong binary. Set it in `Makefile`, `test.sh`, the runner module, and
  CI; never rely on it being inherited.
- **License:** GPLv3 (repo already carries `LICENSE`).
- **Commits are GPG-signed** (repo config already set). Never disable
  signing; if pinentry blocks, retry once, then stop and report.
- **Do not push to GitHub and do not open PRs.** All work stays on local
  branches for review.
- **Generated programs may emit any exit code, 0–255.** The original plan
  capped them at 100 so a shell-reported `$?` could not confuse an exit
  code with a signal death; supervising natively removes the ambiguity, so
  the cap is gone. Exit codes above 128 are now *worth* generating
  deliberately — they are the values that would have been misclassified,
  and a fuzzer should cover them.
- **A nonzero exit is not a finding.** Only: ICE, nasm/ld rejection,
  death by signal, hang, and compile nondeterminism.
- **Every module is `see`-includable and independently testable.** No
  module may call into another module's internals beyond the documented
  function names in its task's Interfaces block.
- **Test convention mirrors the vox repo:** `tests/NNN_name.vox` plus
  `tests/NNN_name.expected`, run by `./test.sh`, which diffs actual
  output against expected. `./test.sh` is the project gate.

## Vox language notes (read before writing any Vox)

These are verified behaviours of vox 0.3.7, confirmed by POC. Ignoring
them will cost you hours.

1. **Function definitions end at a blank line.** A period does not close a
   function body. Without a trailing blank line, every following statement
   is absorbed into the body and the program does nothing — though no
   longer silently: 0.4.x emits `warning: Function 'X' is still open at
   end of file`, so read compiler warnings, not just errors.
2. **`Return a <type>, <expr>.` goes at the END of the body**, not on the
   signature line. Signature: `To name with a number called n.` Body
   statements follow. Last line: `Return a number, total.`
3. **Function calls bind tighter than arithmetic.** `f of n minus 1` means
   `(f of n) minus 1`. There are no parentheses for grouping call
   arguments. **Always precompute:** `a number called next is n minus 1,`
   then `f of next`. Getting this wrong produces silent infinite recursion.
4. **Multiplication is `multiply` or `times`** — the `times` alias shipped
   in 0.4.0 (`Print 6 times 7.` → 42). Both are fine to use; `times` is
   consequently reserved and unavailable as a variable name.
5. **Blank lines close loops.** Never put a blank line inside a `while` or
   `for` body for visual spacing — it terminates the loop early, silently.
5b. **`On error` consumes its whole sentence.** A comma after the
   handler's action binds the NEXT action into the handler too
   (`On error print "x", exit 1.` is one handler, two actions). To guard
   a statement and then continue normally, end the handler with a
   period. This matters doubly for the generator (Task 9): when emitting
   `On error` handlers, terminate them with a period unless the intent
   is genuinely a multi-action handler.
6. **Periods close exactly one nesting level** — the innermost open
   clause, and only that one. Count them deliberately.
6b. **Closing a loop *inside a function* is the trap this project will hit
   most.** A blank line closes a loop (note 5), but inside a function a
   blank line closes the *function* too, so it is unavailable. What closes
   the loop is therefore decided entirely by the loop's **last action**:
   - last action is a plain statement → its period closes the loop, and
     the statements after it belong to the function. **This is the shape
     to write.**
   - last action is a nested `If` → the period closes the `If`, the loop
     stays open, and **every statement that follows is silently swallowed
     into the loop body** and runs once per iteration.

   So when a loop's real last action is an `If`, follow it with a plain
   statement that closes the loop. In the harness that statement is the
   poll delay. Verified against vox 0.4.1; the harness POC failed exactly
   this way before it was corrected.
7. **Some words are reserved and fail as variable or loop names**, with
   misleading errors. Confirmed reserved against 0.4.2 (red-team sweep,
   2026-08-18): `arg`, `args` (alias of `arguments`), `ver` (alias of
   `version`), `flag`, `bigger`, `up`, `ms`, `a`, `times`. NOT reserved,
   despite an earlier version of this note: `b`, `c`, `s`. **`count` is
   legal since vox 0.4.2** (it is contextual: claimed after a possessive
   and in the `the argument count` phrases, ordinary elsewhere) — this
   plan's snippets may use it, and the fuzzer builds against the repo's
   compiler, never an older installed one. Plan 315 in the compiler repo
   will free more property words (`first`, `last`, `second`, `all`,
   `size`, `length`, `capacity`, `raw`, `empty`, …) — until it lands,
   treat those as reserved. The compiler's tip suggests `count_value` /
   `my_count` styles; `docs/STYLE.md` forbids that — pick the thing's
   true name instead (`'the iteration'`, `'programs run'`).
8. **Text accumulation:** `Create a buffer called out.` then
   `a buffer called piece is "text {var}\n".` then `append piece to out.`
   Format strings interpolate variables and expressions and materialize
   as values.
9. **Recursion is depth-limited** and overflow is caught: the program
   prints `Error: stack overflow (recursion depth exceeded)` and exits 1
   rather than crashing.
10. **Out-of-bounds byte reads return 0 and set the error flag** — useful
    as a natural loop terminator when parsing buffers.
11. **Module split:** `see "./util.vox".` at the top of a file includes
    another Vox source; its functions become callable. Paths resolve
    relative to the including file.
12. **`arguments's count` includes argv[0]; `arguments's all` yields
    argv[1..]`.** Loop with `print each item from arguments's all`.
13. **Declare globals; never conjure them with `Set`.**
    `Set findings_dir to "./findings".` on an undeclared name silently
    creates a **number** global holding the string's pointer, which then
    interpolates as `4206732/crash/7`. The declared forms are
    `a text called findings_dir is "./findings".` /
    `a number called total is 0.`; `Set` is for writing to a name that
    already exists (and works fine on a declared text global, including
    from inside a function). The number case (`Set rng_state to 12345.`)
    happens to behave because the inferred type is right — declare those
    too, for the reader if not the compiler.
14. **A string literal in an `If`/`While` condition inside a function
    body is mis-resolved as a variable name** — vox bug #21
    (`docs/BUGS_FOUND.md` in the compiler repo; fix staged as plan 316).
    `If w is not "banana" then,` inside a function fails with
    `Unknown variable: banana`. Until the fix ships, **bind the literal
    to a named local first** and compare against that:
    `a text called 'the hang verdict' is "hang".` then
    `If 'the verdict' is 'the hang verdict' then,`. Top-level
    comparisons and `Return a boolean, w is "x".` are unaffected.

`test.sh` — mirrors the vox repo's runner. Compiles each `tests/*.vox`
with the vox binary, runs it, diffs against the `.expected` file:

```bash
#!/bin/bash
# vox-fuzz test runner — compiles and runs each tests/NNN_*.vox and
# diffs its output against the matching .expected file.

VOX="${VOX:-../vox/target/release/vox}"
# Pin the runtime to the repo's coreasm. Without this an installed
# /usr/share/vox/coreasm silently shadows it and we would be testing the
# packaged compiler runtime instead of the one under development.
export VOX_CORE_PATH="${VOX_CORE_PATH:-$(cd "$(dirname "$VOX")/../.." && pwd)/coreasm}"
# FAIL if the directory does not exist. vox does not error on a bad
# VOX_CORE_PATH - it falls silently through to /usr/share/vox/coreasm,
# so a wrong derivation here (an absolute $VOX, a snapshot binary) would
# have every test quietly exercise the installed packaged runtime.
if [[ ! -d "$VOX_CORE_PATH" ]]; then
    echo "VOX_CORE_PATH '$VOX_CORE_PATH' is not a directory (set VOX_CORE_PATH explicitly)" >&2
    exit 2
fi
VERBOSE=0
[[ "$1" == "-v" || "$1" == "--verbose" ]] && VERBOSE=1 && shift
TARGET="${1:-tests}"

RED='\033[0;31m'; GREEN='\033[0;32m'; NC='\033[0m'
PASSED=0; FAILED=0
WORK="$(mktemp -d)"
trap 'rm -rf "$WORK"' EXIT

if [[ ! -x "$VOX" ]]; then
    echo "vox binary not found at $VOX (set VOX=...)" >&2
    exit 2
fi

if [[ -f "$TARGET" ]]; then
    FILES=("$TARGET")
else
    mapfile -t FILES < <(find "$TARGET" -name '*.vox' | sort)
fi

for f in "${FILES[@]}"; do
    name="$(basename "$f" .vox)"
    exp="$(dirname "$f")/$name.expected"
    [[ -f "$exp" ]] || continue
    bin="$WORK/$name"
    if ! "$VOX" "$f" -o "$bin" > "$WORK/$name.cerr" 2>&1; then
        echo -e "${RED}COMPILE FAIL${NC} $name"
        [[ $VERBOSE == 1 ]] && cat "$WORK/$name.cerr"
        FAILED=$((FAILED+1)); continue
    fi
    # Run from the REPO ROOT: tests reach fixtures (tests/fixtures/...)
    # and the compiler (../vox/...) by repo-relative paths, and their
    # ./vf_* scratch files land here, gitignored and swept after each
    # test. 150s outlasts the longest per-test deadline any test passes
    # to 'run shell' (070's 120s).
    timeout 150 "$bin" > "$WORK/$name.out" 2>&1
    rm -f ./vf_*
    if diff -q "$exp" "$WORK/$name.out" > /dev/null; then
        echo -e "${GREEN}PASS${NC} $name"
        PASSED=$((PASSED+1))
    else
        echo -e "${RED}FAIL${NC} $name"
        [[ $VERBOSE == 1 ]] && diff -u "$exp" "$WORK/$name.out"
        FAILED=$((FAILED+1))
    fi
done

echo "passed: $PASSED  failed: $FAILED"
[[ $FAILED -eq 0 ]]
```

Then `chmod +x test.sh`.

### Task 3: Native process supervision and death classification

**Files:**
- Create: `src/harness.vox`
- Create: `tests/020_harness.vox`
- Create: `tests/020_harness.expected`

**Interfaces:**
- Consumes: nothing.
- Produces:
  - Global `'the last status'` (number) — the raw `wait4` status word from
    the most recent supervised run. `-1` before any run.
  - `supervise with a text called program and a list called 'the argument
    list' and a number called 'the deadline in milliseconds'` → text —
    forks, `Execute`s `program`, polls it against the deadline, kills it
    with signal 9 if it overruns, reaps it, and returns one of `"exit"`,
    `"signal"`, or `"hang"`. The raw status is left in `'the last status'`.
  - `'exit code of' with a number called status` → number.
  - `'signal of' with a number called status` → number.
  - `crashed with a number called status` → boolean.

This is the module the whole tool rests on. **It has been built and run
against vox 0.4.1 before being written down here** — the code below is
transcribed from a working POC, not composed from the documentation.

#### Why this is not the shell wrapper the plan originally specified

The original Task 3 forked `/bin/sh -c "timeout N cmd; echo $? > file"` and
parsed the exit code back out of the file, because vox 0.3.7 gave a Vox
program no way to see a child's wait status. Three features shipped in
0.4.0 remove that need entirely:

- `reap ... without waiting` — `wait4` with `WNOHANG`. Returns the child's
  pid when it has finished, `0` when it is still running (**not** an
  error — that distinction is the whole point of the form), negative on a
  real error.
- `Send signal N to process <pid>` — `kill(2)`, so the harness enforces its
  own deadline and needs no coreutils `timeout`.
- `the reaped status` — the kernel's raw `int status`, undecoded, from the
  most recent *successful* reap. `-1` before any reap, a sentinel no real
  status can take.

Beyond removing two runtime dependencies, this is a **correctness** fix.
`$?` from a shell reports `128+N` for a signal death, which is
indistinguishable from a program that legitimately exits with that code —
`exit 139` and "killed by SIGSEGV" arrive as the same number. That
ambiguity was the only reason the original plan forbade exit codes above
100. A real wait status keeps the signal in the low 7 bits and the exit
code in the next 8, so they cannot collide.

`examples/supervisor.vox` in the compiler repo is this same loop as a
runnable program; read it before starting.

#### The loop shape is load-bearing — read note 6b first

The `While` loop below ends with a plain `Wait 5 milliseconds.` statement,
and that is deliberate. A period closes only the innermost open clause. If
the loop's last action were the nested `If`, the period would close the
`If` and leave the loop open, and **every statement after it — the status
read, the verdict returns — would be swallowed into the loop body** and run
once per iteration. A blank line would close the loop, but inside a
function a blank line closes the function too.

The POC this task is transcribed from failed in exactly that way before it
was corrected. Do not rearrange the tail of this loop.

The cost is one 5ms delay on the final iteration, after the child has
already been reaped. That is deliberate and worth it; do not "optimise" it
away by moving the `Wait` inside the `If`.

- [ ] **Step 3: Write the implementation**

`src/harness.vox` — transcribed from the verified POC:

```
(Run a program, and learn how it died.

 A fuzzed program can meet three fates and the harness must tell them
 apart exactly: it exits with a code of its own, a signal kills it, or it
 never finishes and the harness has to end it. All three are read from the
 kernel's own wait status, so no fate can be mistaken for another.

 The decoders are written out here rather than taken from vox-libs'
 process library on purpose: the fuzzer must run on a machine with nothing
 installed, and these are four lines of arithmetic.)

To 'exit code of' with a number called status.
  Return a number, status divide 256 modulo 256.

To 'signal of' with a number called status.
  Return a number, status bit-and 127.

To crashed with a number called status.
  a number called 'terminating signal' is status bit-and 127.
  Return a boolean, 'terminating signal' is not 0.

Set 'the last status' to -1.

(Run a program to completion, or to the deadline, whichever comes first.
 Returns how it ended; the raw wait status is left in 'the last status'.

 The argument list is argv[1..]: Vox prepends the program path as argv[0]
 itself, so naming it again in the list passes it to the program as a real
 argument.)
To supervise with a text called program and a list called 'the argument list' and a number called 'the deadline in milliseconds'.
  a number called 'the child' is fork the process.
  If 'the child' is 0 then,
      Execute program with arguments 'the argument list',
      Exit 127.
  a timer called clock.
  Start the clock.
  a number called 'reap result' is 0.
  a boolean called 'the child is still running' is true.
  a boolean called 'the child was killed' is false.
  While 'the child is still running',
      Set 'reap result' to reap child 'the child' without waiting,
      If 'reap result' is 'the child' then,
          Set 'the child is still running' to false.
      If 'the child is still running' then,
          a number called 'milliseconds waited' is the clock's elapsed in milliseconds,
          If 'milliseconds waited' is greater than 'the deadline in milliseconds' then,
              Send signal 9 to process 'the child',
              Set 'reap result' to reap child 'the child',
              Set 'the child is still running' to false,
              Set 'the child was killed' to true.
      Wait 5 milliseconds.
  Set 'the last status' to the reaped status.
  If 'the child was killed' then,
      Return a text, "hang".

death as its own `128+N` exit code.

gains fd redirection, this helper disappears.

**Interfaces:**
- Consumes: `'rng seed'`, `'rng next'`, `'rng below'` (Task 2).
- Produces:
  - Global `gen_out` (buffer) — the generated program text.
  - Global `gen_vars` (number) — count of declared variables, used to

  - `'gen program' with a number called seed and a number called budget`

Generation rules (hard requirements):
- Every variable is declared before use; names are `v1..vN` in order.
- `Exit` codes are `'rng below' of 256` — the full range. Codes above
  128 are deliberately in play (Global Constraints): they are the values
  a shell-reported status would conflate with signal deaths, and only
  the native harness classifies them correctly.
- Nesting depth is capped at 3; the depth parameter decrements on each
  recursive call and MUST be precomputed into a local first (language
  note 3).
- No blank lines inside loop or conditional bodies (language note 5).
- No `mount`, `reboot`, `shutdown`, device-node, `chroot`, or
  absolute-path file actions — generated programs must not be able to
  affect anything outside their working directory.

- Produces:

  - `'fuzz gen once' with a number called seed and a number called budget
    and a number called 'the deadline in milliseconds'` → number —
    generates, compiles, runs, and classifies one program; records a
    finding when warranted; returns `1` if a finding was recorded, `0`
    otherwise.
  - `'fuzz gen run' with a number called 'the first seed' and a number
    called 'how many programs' and a number called budget and a number
    called 'the deadline in milliseconds'` — runs the loop and prints the
    summary. (`count` was this parameter's natural name and is currently
    a reserved word; a fix is in flight in the compiler repo. Until it
    lands, `'how many programs'` is the true name spelled out.)

Classification rules inside `'fuzz gen once'` — this is the heart of the
tool, and each branch maps to a Global Constraint. Compiling and running
report through different channels, and the difference is the design:

**Compile classification** (a number, from `'compile vox'` via the shell),
in this order:
- `-1` → `supervise` saw something other than a plain exit from the shell
  itself → finding, category `ice` (detail: "compiler run did not exit").
  This also covers a `/bin/sh` that exec-optimizes: ours does not for a
  redirected command, and the compile command's `> ./vf_cerr 2>&1`
  redirection is **load-bearing** for exactly that reason — it forces the
  shell to fork, so a compiler signal death arrives as the shell's
  `128+N` exit rather than vanishing. Never remove the redirection.
- exit code `> 128` → the shell saw the compiler die by signal → finding,
  category `ice`.
- exit code `101` → **a Rust panic** → finding, category `ice`. The vox
  binary is built without `panic = "abort"`, so an `unwrap()` or index
  panic in the compiler unwinds and exits 101 — the single most likely
  ICE shape, and the original plan's `> 128`-only rule silently discarded
  it into the "generator bug" band. (vox's deliberate exit codes are 0
  and 1 on the compile path, so 101 cannot be an honest compile error.)
- other nonzero: grep the captured stderr —
  `'run shell' of "grep -q -e nasm -e 'ld:' ./vf_cerr" and 5000` — and on
  a hit record category `asm-reject` (vox emitted assembly that nasm or
  ld refused: a code-generation bug, invariant #2). On no hit, **not** a
  finding (generator bug); count it and skip.

**Run classification** (a verdict text, from `'run program'` via
`supervise`, with the raw status in `'the last status'`):
- `"hang"` → finding, category `hang`
- `"signal"` → finding, category `crash`; the detail records
  `'signal of' of 'the last status'`
- `"exit"` → clean, not a finding, whatever the exit code — including
  codes above 128, which only the native harness can classify correctly

 earlier draft called a 'parse status file' function that no task

 replacement, defined where it is used.)

    open a file for reading called 'the number file' at path.
    a buffer called 'the digits' is 64 bytes in size.

    While 'the byte' is greater than 47,
        Set 'the value' to 'the value' multiply 10,
        Set 'the value' to 'the value' add 'the byte',
        Set 'the value' to 'the value' minus 48,

        Set 'the byte' to byte 'the byte position' of 'the digits'.

    a number called 'the compiler exit code' is 'compile vox' of path and "./vf_red_bin".
    If 'the compiler exit code' is greater than 0 then,
        Return a text, "compile-error".
    a text called 'the verdict' is 'run program' of "./vf_red_bin" and 'the deadline in milliseconds'.
    a text called 'the exit verdict' is "exit".
    If 'the verdict' is 'the exit verdict' then,
        a number called 'the exit code' is 'exit code of' of 'the last status',
        If 'the exit code' is 0 then,
            Return a text, "exit-zero".
        Return a text, "exit-nonzero".
    Return a text, 'the verdict'.

(One pass over the lines, last to first, so a removal never shifts the
 index of a line not yet tried. A second pass only runs while passes keep
 making progress, up to the attempt budget.)
To 'reduce file' with a text called path and a text called 'the verdict to preserve' and a number called 'the deadline in milliseconds'.
    a number called attempts is 0.
    a number called 'this pass removed lines' is 1.
    While 'this pass removed lines' is 1,
        Set 'this pass removed lines' to 0,
        a number called 'the line under trial' is 'line count' of path,
        While 'the line under trial' is greater than 0,
            a number called 'the backup result' is 'run shell' of "cp {path} ./vf_red_backup" and 5000,
            a number called 'the removal result' is 'run shell' of "sed -i '{'the line under trial'}d' {path}" and 5000,
            a text called 'the verdict' is 'verdict of file' of path and 'the deadline in milliseconds',
            If 'the verdict' is 'the verdict to preserve' then,
                Set 'this pass removed lines' to 1.
            If 'the verdict' is not 'the verdict to preserve' then,
                a number called 'the restore result' is 'run shell' of "cp ./vf_red_backup {path}" and 5000.
            Set attempts to attempts add 1,
            If attempts is greater than 200 then,
                Set 'the line under trial' to 0,
                Set 'this pass removed lines' to 0.
            Set 'the line under trial' to 'the line under trial' minus 1.
    a number called 'the final line count' is 'line count' of path.
    Return a number, 'the final line count'.
```

The control flow here is the most period-sensitive in the project; two
shapes in it are deliberate and load-bearing:

- **Both `While` loops end on a plain statement** (the decrement inside,
  the line-count read after), per language note 6b. The original draft of
  this function ended the inner loop on a nested `If`, which note 6b shows
  silently swallows every following statement into the loop body.
- **The backward walk** (last line to first) means a successful removal
  never renumbers a line that has not been tried yet, so there is no
  conditional index bookkeeping to get wrong.

Verify the format string `{'the line under trial'}` interpolates a quoted
identifier inside a shell command correctly before relying on it; if it
does not, precompute the command text from a plain-named local first.

`'fuzz input run'` compiles the target once, then loops: mutate the seed
input, run the binary with that input on stdin, classify by the supervise
verdict, and save `crash` or `hang` findings with the offending input
copied into the finding directory as `input.bin`. Add the `input`
subcommand to `src/main.vox` following the `gen` pattern.

Running the target needs stdin plumbed in — which Vox cannot do — AND the
target's true wait status — which a plain `'run shell'` destroys, because
sh absorbs a child's signal death into its own exit code `128+N`. **`exec`
resolves the conflict**: supervise `/bin/sh` with the argument list
`["-c", "exec {binpath} < {inpath}"]`, so the shell sets up the
redirection and then *replaces itself* with the target in the same
process; the status supervise reaps is the target's own. Verified against
vox 0.4.1 before this revision: the same segfaulting child classifies as
`exit code 139` without `exec` and as `signal 11` with it. The mutated
input file's name must therefore contain no shell-special characters —
keep it fixed (`./vf_mut_input`) rather than deriving it from data.

## Reporting findings

Any genuine finding — a generated program that makes vox ICE, emit
rejected assembly, produce a binary that dies by signal, hang, or compile
nondeterministically — is a **vox compiler bug**, not a vox-fuzz bug.

When one appears:
1. Confirm it reproduces from the saved `repro.sh`.
2. Let the reducer shrink it, then confirm the reduced program still
   fails.
3. Report it to the master with the reduced `.vox` source, the seed, the
   classification, and the vox version.
4. **Do not fix the vox compiler from this repo.** Do not push, and do
   not open GitHub issues — the master routes findings to Josj.
